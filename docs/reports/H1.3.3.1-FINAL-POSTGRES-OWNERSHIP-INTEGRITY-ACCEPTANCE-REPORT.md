## 2. Failure Root Cause Analysis & Remediation Details

### Failure 1: H133-04 — Tenant Isolation Fixture Mismatch

#### Root Cause
Under CREDVAIL's multi-tenant architecture, a user wallet is user-scoped and may legitimately hold claimed credentials from multiple distinct institutions, provided each individual claim is consistent (i.e. `ClaimInvitation.tenantId === CredentialRecord.tenantId`).
In the original fixture setup of `test/integration/postgres-wallet-ownership.test.ts`, the adversarial foreign fixture was created as:
- `credForeignTenant.tenantId = foreignTenantId`
- `invForeign.tenantId = foreignTenantId`
Because `invForeign.tenantId === credForeignTenant.tenantId`, Alice's claim of that credential was evaluated as legitimate by `PrismaWalletCredentialRepository.listClaimedCredentials(userIdAlice)`. The relational check `inv.credential.tenantId !== inv.tenantId` did not trigger because both IDs were `foreignTenantId`. Consequently, the credential appeared in Alice's wallet, failing the assertion `expect(creds.some(c => c.credentialId === credForeignTenant.credentialId)).toBe(false)`.

#### Remediation
1. Updated `invForeign` creation so that `invForeign.tenantId = tenantId` (the primary test tenant) while `credForeignTenant.tenantId = foreignTenantId`.
2. This establishes an intentional, malicious cross-tenant mismatch where an invitation in Tenant A references a credential issued by Tenant B.
3. When `listClaimedCredentials(userIdAlice)` executes, the strict relational integrity check:
   ```ts
   if (
     !inv.credential ||
     inv.credential.credentialId !== inv.credentialId ||
     inv.credential.tenantId !== inv.tenantId ||
     !inv.credential.recipient ||
     !inv.tenant
   ) {
     continue;
   }
   ```
   detects `foreignTenantId !== tenantId` and excludes the corrupted record.
4. Strengthened `H133-04` by asserting both wallet exclusion and authoritative ownership rejection:
   ```ts
   expect(creds.some((c) => c.credentialId === credForeignTenant.credentialId)).toBe(false);
   expect(
     await WalletCredentialRepository.userOwnsCredential(
       userIdAlice,
       credForeignTenant.credentialId,
       credForeignTenant.certificateNumber
     )
   ).toBe(false);
   ```

### Failure 2: H133-11 — Cryptographic Verification Evidence & Key PEM Reconstruction

#### Root Cause
1. **Missing Merkle Evidence & Leaf Hash Tamper Mismatch**: In `test/integration/postgres-wallet-ownership.test.ts`, Alice's `CredentialRecord` fixture was seeded with a hardcoded placeholder `leafHash: "leaf_hash_alice"` and `vcPayloadJson: signedVcAlice` with no Merkle inclusion proof attached.
   During `POST /api/v1/wallet/present`, `VerificationService.evaluateCredentialCore` executed the 5-layer cryptographic engine:
   - **Layer 2 (RFC 8785 Canonical JSON Recalculation)**: Computed `recalculatedLeafHash = VcService.computeLeafHash(...)` from the payload claims and compared it with stored `cred.leafHash` (`"leaf_hash_alice"`). Because `"leaf_hash_alice" !== recalculatedLeafHash`, `RFC8785_CANONICAL_HASH` failed with tamper detection.
   - **Layer 4 (Merkle Inclusion Proof)**: No proof was embedded in `vcPayload.evidence`, and `CredentialRepository.getMerkleProof()` found no batch tree. `MERKLE_INCLUSION_PROOF` failed.
   - As a result, `json.data.verificationResult.isValid` returned `false`.
2. **Empty Issuer Public Key PEM from PostgreSQL**: In `src/lib/repositories/key-repository.ts`, methods `getActiveKey`, `getKeyByEpoch`, and `listKeys` reconstructed `StoredIssuerKey` objects from PostgreSQL records with hardcoded `publicKeyPem: ""`. When `VerificationService` called `VcService.verifyCredentialSignature(vcPayload, issuerKeyRecord.publicKeyPem)`, the empty PEM caused signature verification to fail.

#### Remediation
1. **Dynamic PEM Reconstruction**: Enhanced `KeyRepository.getActiveKey`, `KeyRepository.getKeyByEpoch`, and `KeyRepository.listKeys` to dynamically recover the SPKI PEM via `KeyService.multibaseToPublicKeyPem(found.publicKeyMultibase)` whenever retrieving issuer keys from PostgreSQL:
   ```ts
   let pem = "";
   try {
     pem = KeyService.multibaseToPublicKeyPem(found.publicKeyMultibase);
   } catch {
     // fallback
   }
   // publicKeyPem: pem
   ```
2. **Cryptographic Merkle Evidence in Fixture**: In `test/integration/postgres-wallet-ownership.test.ts`:
   - Computed deterministic VC hash: `const vcHashAlice = VcService.computeVcHash(signedVcAlice);`
   - Computed Section 5.1 leaf hash: `const leafHashAlice = VcService.computeLeafHash(credIdAlice, certNumAlice, vcHashAlice);`
   - Built single-leaf Merkle tree: `const aliceMerkleTree = VcService.buildBatchMerkleTree([leafHashAlice]);`
   - Generated inclusion proof: `const aliceMerkleProof = VcService.generateMerkleProof(aliceMerkleTree, 0);`
   - Attached proof into credential evidence block: `signedVcAlice = VcService.attachMerkleProof(signedVcAlice, aliceMerkleProof, batchId);`
   - Updated `issuanceBatch` with `merkleRoot: aliceMerkleProof.root, leafCount: 1`.
   - Persisted genuine `leafHash: leafHashAlice` into `credAlice`.
3. **Comprehensive Assertion Gate in H133-11**: Verified `isValid === true` and verified all 7 critical checks passed:
   ```ts
   const checkMap = new Map(
     json.data.verificationResult.checks.map((c: any) => [c.code, c.passed])
   );
   expect(checkMap.get("HOLDER_PRESENTATION_SIGNATURE")).toBe(true);
   expect(checkMap.get("CHALLENGE_NONCE_VERIFICATION")).toBe(true);
   expect(checkMap.get("W3C_SCHEMA_CONFORMANCE")).toBe(true);
   expect(checkMap.get("RFC8785_CANONICAL_HASH")).toBe(true);
   expect(checkMap.get("ECDSA_P256_SIGNATURE")).toBe(true);
   expect(checkMap.get("MERKLE_INCLUSION_PROOF")).toBe(true);
   expect(checkMap.get("REVOCATION_STATUS")).toBe(true);
   ```
