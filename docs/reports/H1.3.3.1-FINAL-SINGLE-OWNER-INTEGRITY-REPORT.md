## 2. PostgreSQL Index Predicate Normalization & Catalog Verification

File: [prisma/sql/h1-3-3-verify-single-owner-index.sql](file:///f:/CredVail/prisma/sql/h1-3-3-verify-single-owner-index.sql)

### 2.1 Predicate Normalization
PostgreSQL renders stored index predicates via `pg_get_expr(i.indpred, i.indrelid)` with identifier quotes and parentheses, e.g.:
```sql
(("consumedAt" IS NOT NULL) AND ("claimedByUserId" IS NOT NULL))
```
Direct literal string comparison fails due to dialect formatting. As finalized in H1.3.3.1-H1, the verifier normalizes identifier quotes, parentheses, case, and collapses repeated whitespace to a single space:
```sql
v_pred_normalized := trim(regexp_replace(lower(replace(replace(replace(v_raw_pred, '"', ''), '(', ''), ')', '')), '\s+', ' ', 'g'));

IF v_pred_normalized <> 'consumedat is not null and claimedbyuserid is not null' THEN
  RAISE EXCEPTION 'H1.3.3.1 index verification failed: index predicate does not exactly match expected single-owner invariant (expected: "consumedat is not null and claimedbyuserid is not null", got: "%")', v_pred_normalized;
END IF;
```
Exact equality ensures no additional predicates, missing conditions, or narrowed predicates are accepted.

## 3. Ownership-State Monotonicity & PostgreSQL Trigger Safeguard

### 3.1 Monotonicity & Paired State Invariants
The single-owner partial unique index applies only while `consumedAt IS NOT NULL AND claimedByUserId IS NOT NULL`. To ensure defense-in-depth against accidental unconsuming, claimant reassignment, one-sided states, or field nullification via raw SQL, maintenance scripts, or direct database mutations, PostgreSQL-level trigger safeguards enforce strict ownership monotonicity and paired-field consistency across both INSERT and UPDATE:

1. **Paired Ownership State (INSERT & UPDATE):**
   - Unclaimed invitation: `consumedAt IS NULL AND claimedByUserId IS NULL`.
   - Claimed invitation: `consumedAt IS NOT NULL AND claimedByUserId IS NOT NULL`.
   - Any write producing `(consumedAt IS NULL) IS DISTINCT FROM (claimedByUserId IS NULL)` is rejected with SQLSTATE `23514`.
2. **One-Way Consumption:** An unconsumed invitation can transition to consumed once.
3. **Permanent Consumption Timestamp:** Once set, `consumedAt` can never be reset to `NULL` or altered.
4. **Permanent Claimant Assignment:** Once assigned, `claimedByUserId` can never be cleared to `NULL` or reassigned to another user account.
5. **Permanent Credential Binding:** `credentialId` is strictly immutable once created.
6. **Safe Operation Separation:** `OLD` is only accessed on `UPDATE`, never on `INSERT`.

### 3.2 Immutability Trigger Implementation
Files: [prisma/sql/h1-3-3-ownership-monotonicity-trigger.sql](file:///f:/CredVail/prisma/sql/h1-3-3-ownership-monotonicity-trigger.sql) and [prisma/sql/h1-3-3-verify-ownership-trigger.sql](file:///f:/CredVail/prisma/sql/h1-3-3-verify-ownership-trigger.sql)

```sql
CREATE OR REPLACE FUNCTION trg_enforce_claim_invitation_monotonicity()
RETURNS TRIGGER AS $$
BEGIN
  -- Invariant 0: Paired ownership-state invariant (both NULL or both NOT NULL)
  IF (NEW."consumedAt" IS NULL) IS DISTINCT FROM (NEW."claimedByUserId" IS NULL) THEN
    RAISE EXCEPTION 'claim_invitations ownership state violation: consumedAt and claimedByUserId must both be NULL or both be NOT NULL (paired ownership state)'
      USING ERRCODE = '23514';
  END IF;

  -- The following immutability rules apply only to UPDATE operations (never access OLD on INSERT)
  IF TG_OP = 'UPDATE' THEN
    IF OLD."credentialId" IS DISTINCT FROM NEW."credentialId" THEN
      RAISE EXCEPTION 'claim_invitations ownership violation: credentialId is immutable once created (attempted to change % to %)',
        OLD."credentialId", NEW."credentialId"
        USING ERRCODE = '23514';
    END IF;

    IF OLD."consumedAt" IS NOT NULL THEN
      IF NEW."consumedAt" IS NULL THEN
        RAISE EXCEPTION 'claim_invitations ownership violation: consumedAt cannot be reset to NULL once consumed'
          USING ERRCODE = '23514';
      END IF;
      IF OLD."consumedAt" IS DISTINCT FROM NEW."consumedAt" THEN
        RAISE EXCEPTION 'claim_invitations ownership violation: consumedAt is immutable once set (attempted to change % to %)',
          OLD."consumedAt", NEW."consumedAt"
          USING ERRCODE = '23514';
      END IF;
    END IF;

    IF OLD."claimedByUserId" IS NOT NULL THEN
      IF NEW."claimedByUserId" IS NULL THEN
        RAISE EXCEPTION 'claim_invitations ownership violation: claimedByUserId cannot be cleared once assigned'
          USING ERRCODE = '23514';
      END IF;
      IF OLD."claimedByUserId" IS DISTINCT FROM NEW."claimedByUserId" THEN
        RAISE EXCEPTION 'claim_invitations ownership violation: claimedByUserId is immutable once assigned (attempted to change % to %)',
          OLD."claimedByUserId", NEW."claimedByUserId"
          USING ERRCODE = '23514';
      END IF;
    END IF;
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_claim_invitation_monotonicity ON "claim_invitations";

CREATE TRIGGER trg_claim_invitation_monotonicity
BEFORE INSERT OR UPDATE ON "claim_invitations"
FOR EACH ROW
EXECUTE FUNCTION trg_enforce_claim_invitation_monotonicity();
```

## 4. Account-Deletion Ownership Lifecycle & Schema Hardening

### 3.1 Problem Identified
The initial Prisma schema mapped `claimedByUser` as:
```prisma
claimedByUser User? @relation(fields: [claimedByUserId], references: [id], onDelete: SetNull)
```
If an authenticated claimant account was hard-deleted, PostgreSQL would execute `ON DELETE SET NULL`, setting `claimedByUserId = NULL`. Because the partial unique index predicate requires `"claimedByUserId" IS NOT NULL`, the row would be dropped from the partial index, improperly releasing the single-owner slot and allowing a second claimant to claim the same credential.

### 3.2 Solution: Database-Enforced Restrictive Deletion Policy
In [prisma/schema.prisma](file:///f:/CredVail/prisma/schema.prisma):
```prisma
model ClaimInvitation {
  ...
  claimedByUser User? @relation(fields: [claimedByUserId], references: [id], onDelete: Restrict)
}
```

### 3.3 Security & Lifecycle Invariants:
1. **Hard Deletion Blocked:** Any attempt to hard-delete a `User` account that owns a claimed credential fails immediately with a PostgreSQL foreign key RESTRICT error (`23503` / Prisma `P2003`).
2. **Permanent Ownership Slot:** `claimedByUserId` can never be silently cleared by account deletion.
3. **No Credential Release:** A second pending invitation for the same `credentialId` remains permanently unclaimable.
4. **Account Lifecycle & Deactivation:** In CREDVAIL, user accounts requiring termination are soft-deactivated or anonymized at the application layer; their durable ownership records and audit logs remain immutable.
5. **No Automatic Reassignment:** Administrative ownership transfers (if ever required) must be executed through explicit, auditable administrative workflows—never via cascade deletion or implicit nullification.

## 4. Precise Unique-Constraint Classification Architecture

File: [src/lib/repositories/claim-invitation-repository.ts](file:///f:/CredVail/src/lib/repositories/claim-invitation-repository.ts)

### 4.1 Four-Case Classification Matrix

The Prisma schema declares `credentialId String @unique` on `CredentialRecord` in addition to the partial unique index on `ClaimInvitation`. A collision on `CredentialRecord.credentialId` must never be misclassified as `CREDENTIAL_ALREADY_CLAIMED`.

| Case | Error Shape | Resolution Mechanism | Result |
|---|---|---|---|
| **Case A: Explicit Index Identity** | `err.message` or `err.meta.target` explicitly contains `claim_invitations_one_consumed_owner_per_credential_uq` | Direct identification | Throws typed `CredentialAlreadyClaimedError` (HTTP 409). |
| **Case B: Ambiguous Unique Error (Confirmed Duplicate)** | Prisma `P2002` (e.g. `meta.target = ["credentialId"]`) or Postgres `23505` without explicit index name | Post-failure database recheck: queries for existing consumed claim on `targetCredId` where `id != invitationId` | If another committed consumed owner is found, throws `CredentialAlreadyClaimedError` (HTTP 409). |
| **Case C: Ambiguous Unique Error (Unrelated Conflict)** | Prisma `P2002` on `CredentialRecord.credentialId`, duplicate `tokenHash`, or internal collision | Post-failure database recheck finds NO other consumed owner for `targetCredId` | **Rethrows the original database error untouched** (never maps to 409). |
| **Case D: Raw SQLSTATE 23505** | Raw PostgreSQL unique violation | Only mapped directly if constraint name is confirmed; otherwise routes to safe recheck | Preserves original SQL error if unconfirmed. |

### 4.2 Non-Retryable Conflict Rule
In `isRetryableTransactionConflict(err)`:
- Any unique-constraint violation (`isAnyUniqueViolation(err)`) immediately returns `false`.
- Deterministic constraint failures fail fast without wasting whole-transaction retry attempts.
- The transaction rolls back cleanly; `consumedAt` and `claimedByUserId` remain `NULL`.
